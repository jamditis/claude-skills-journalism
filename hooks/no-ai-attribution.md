# No AI attribution

When a `git commit`, a `gh pr create`, or a `gh pr comment` is about to run, check the message it carries for AI authorship credit and stop the action if it finds any. The published record of who wrote what should name people, not tools. A "generated with" line in a commit, a `Co-Authored-By` trailer naming a model, or a tool credit in a PR body all put a machine's name where a contributor's belongs, and once it is in git history or on a merged PR it is part of the project's provenance for good.

For a newsroom the stakes are higher than tidiness. Bylines and authorship are an editorial commitment: a reader, an editor, or a source who follows the trail should find the person accountable for the work, not a model version. This hook keeps that line clean at the moment the credit would otherwise enter the record.

## When it runs

On a `Bash` tool call whose command writes a message into the project record:

- `git commit`, checked against the commit message whether it is inline (`git commit -m`, `git commit -am`) or read from a file the command names (`git commit -F <file>`, `git commit --file <file>`, or a `git commit -t <file>`/`--template <file>` whose contents preload the message), and including a `git commit` chained after `&&`, `||`, `;`, or a pipe. Its author and trailer fields (`--author`, `--trailer`) are checked too, since those write authorship directly into the commit.
- `gh pr create` and `gh issue create`, checked against the body (inline `--body`, a named `--body-file <file>`, or a `--template <file>`) and the title (`--title`). With `--body-file`/`--template` and no `--title`, `gh` prompts for the title interactively after the hook runs, so the title is not seen in that case.
- `gh pr edit` and `gh issue edit`, checked against the new title (`--title`) and body (`--body` or `--body-file <file>`), since editing after creation is another way a credit reaches the record.
- `gh pr comment`, `gh issue comment`, and `gh pr review`, checked against the comment or review body, including a `--body-file <file>` body.

Anything else passes straight through. The check reads the message text the command submits, not the diff: inline, from a file the command names by path, or from an author/trailer field. A file argument of `-` (`git commit -F -`, `gh pr create --body-file -`) reads the message from stdin, which a pre-command hook cannot inspect, so those forms are not checked. The same holds for a message the shell computes at run time rather than one written literally: a command substitution or process substitution (`git commit -m "$(cat MSG)"`), or a message file created earlier in the same command line (`printf '...' > MSG && git commit -F MSG`), has no literal text for a pre-command check to read at hook time, so it passes. Catching the same-command file case would mean modeling the output of every writer (`printf`, `echo`, `tee`) and scanning every command's arguments, which would defeat the subject-of-the-work allowance.

A commit's `--author` and `--trailer` fields, `gh pr create --template <file>`, and the whole `gh pr edit` subcommand were the flag-level bypasses of an earlier message-text-only guard; the executable closes them (#177). An author or trailer field is read as authorship: a tool or bot name there blocks even with a human-looking email, because an author field is a byline by definition. A template file is read like a message file: gh's `--template` like a `--body-file`, and git commit's `-t`/`--template` like a `--file`. Git's long options are matched the way git resolves them: an unambiguous prefix counts, so `git commit --au "Claude <c@example.com>"` sets the author and is read as one, while an ambiguous prefix that git itself rejects (`--a`) is left alone. gh does not prefix-match, so its flags are matched only in full. A bare `--` ends option parsing for git and gh alike: a byline-looking token after it is a pathspec (a filename), not message text, so `git commit -- --message "..."` is not scanned as a message.

The command word is found even when it is not the first token. Leading environment assignments and an `env` wrapper are stepped over (`GH_TOKEN=x gh pr create ...`, `env GIT_AUTHOR_NAME=Claude git commit ...`), including the `env -S` split-string form in its spaced, attached, and `=` spellings (`env -S "..."`, `env -S'...'`, `env --split-string=...`), whose packed command is expanded and checked. An `env -C <dir>` run directory is honored in the same three spellings (`env -C dir`, `env -Cdir`, `env --chdir=dir`), and an `env --` that ends option parsing still has its following `NAME=value` operands read as assignments. Commands separated by shell operators or by a newline are each checked, whether or not the operator is spaced (`a&&git commit ...`, `(git commit ...)`, and a `git commit` on its own line after another command); a run of operator characters that the tokenizer glues into one token, such as a subshell close and separator (`(cd x); git commit ...`), still splits the commands. A command hidden behind a leading shell control keyword (`if ok; then git commit ...`, `while git commit ...`) is reached by peeling the keyword. A `gh` write command is recognized by its group and subcommand tokens regardless of any global flags before them (`gh -R owner/repo pr create ...`, `gh --hostname h pr create ...`). Commit identity set outside the message is read as authorship, the same as `--author`: the environment vars (`GIT_AUTHOR_NAME`, `GIT_COMMITTER_NAME`, and their email vars), whether set as an inline prefix or exported by an earlier `export` in the same command (a later re-export or `unset` updates the value the way the shell would), and the inline config form `git -c user.name=... -c user.email=... commit`. A message written with ANSI-C quoting (`git commit -m $'subject\n\nGenerated with Claude'`), where the shell turns `\n` into a real newline before the command runs, has those escapes decoded so the byline lands on its own line the same way the shell will write it.

A named message file is read from the directory the command would run in, not blindly from the payload's `cwd`: a preceding `cd <dir>`, a `git -C <dir>`, or an `env -C <dir>` moves where a relative `-F`/`--body-file`/`--template` path resolves (`cd repo && git commit -F MSG` reads `repo/MSG`). Directory tracking is a best effort, because a pre-command hook cannot run the shell: a `cd` inside a subshell (`(cd repo); git commit ...`) does not actually persist, and a `cd` to a missing directory does not actually move. So a relative file is resolved against both the tracked directory and the payload's `cwd`, and a match in either blocks. Reading both makes a wrong guess about the directory a false positive at worst, never a missed byline. A `~`-prefixed file is read both as a literal `cwd`-relative path and as a home-expanded path, since the quoting that decides which the shell means is gone by tokenization; either interpretation blocks. Only a regular file is read, up to a size cap; a FIFO or device named as the file is treated as unreadable and passes, so the hook cannot block on a read.

One known false positive follows from splitting a command on its newlines: a watched command written inside a here-document body (`cat <<'EOF' > notes.txt` ... `git commit -m "..."` ... `EOF`) is checked as if that body line were a real command, so an attributed example inside documentation can trip the hook. The body is data, not a command the shell runs, so this over-blocks in the safe direction; the fix is to reword the example or split it across a run.

Because the hook binds to the `Bash` tool, it only sees these commands when they run as shell calls. A commit, PR, or comment made through a non-Bash path (an IDE's git integration, the GitHub web UI, or an MCP GitHub connector) does not pass through it, so it guards the command-line workflow rather than every write to the record. The same holds for a message posted through a raw `gh api` call (for example a review-thread reply to `repos/{owner}/{repo}/pulls/{n}/comments/{id}/replies`): the match keys on the `git` and `gh` subcommands listed above, not on arbitrary API URLs.

Two command forms carry no message text for a pre-command check to read, so they pass through: a bare `git commit` that opens an editor for the message (no `-m` or `-F`), and `gh pr create --fill`, `--fill-verbose`, or `--fill-first`, which assemble the title and body from the branch's commits. A filled body is only as clean as those commits. The hook screens the commit messages it can read, but a `--fill` body can also draw on commits it never screened: ones that predate its install, ones made through a path it does not watch (an IDE, the web UI, a connector), and even command-line commits whose message it could not read (a bare-editor commit, or `-F -` from stdin). So `--fill` is not a guarantee that the resulting body was screened.

## What it flags

The message is refused when it carries author credit to an AI tool, model, or vendor. The patterns it looks for:

- An attribution verb (generated, created, written, authored, made, built, produced, assisted, co-authored, powered) joined by "with", "by", "using", or "via" to an assistant, model, or company name, when it leads a line: "Generated with Claude Code", "Written by ChatGPT", "Generated using Claude Code". The credited name can be a bare "AI" with no model ("Generated with AI", "Written by AI"), and the verb can carry an "AI-" prefix ("AI-assisted by Claude", "AI-generated with GPT-4"). The standalone-"AI" credit is distinguished from the adjective "AI-<noun>" of subject matter, so "Built with AI-powered search" describes the feature and passes.
- A `Co-Authored-By:` trailer whose name or email points at a model or tool rather than a person.
- "AI-assisted" or "AI-generated" standing on its own as a sign-off line, or a robot-emoji byline (the emoji leading a line, or sharing a line with an attribution phrase). A robot emoji embedded in ordinary prose, such as "fix the robot-emoji glyph in Slack", is subject matter and passes.

Naming a tool as the *subject* of the work is fine: "switch the parser to the new tokenizer" or "document the Claude API client" describes the change and is not a byline. The hook targets credit lines, not every mention of a tool. A bare model name on its own is treated the same way: in free prose it is subject matter, so a model-comparison list ("- Claude", "- GPT-4") passes, and a credit needs one of the cues above to block (a verb-plus-tool byline, the "AI-assisted"/"AI-generated" or robot-emoji sign-off, or a `Co-Authored-By` value). A bare name blocks only in an author or trailer field, where it is authorship by definition (see below). Line position is the discriminator for the verb-plus-tool form: "Generated with Claude Code" leading a line is a byline and is refused, while the same words mid-sentence describe the subject and pass ("handle summaries generated by Claude", "flag posts written by GPT bots"). The same holds for "AI-assisted"/"AI-generated": "detect AI-generated images in uploads" and "add AI-assisted analysis" describe what the change is about, so they pass, while a bare "AI-assisted" line at the end of a message reads as a byline and is refused. The trade is deliberate: a credit that names a tool mid-sentence rather than at the start of a line can slip, but the emitted attribution forms lead their line, and the tool-name, emoji, and `Co-Authored-By` checks cover the ones that actually get written.

The exception is the author and trailer fields. Those are strict: any model, tool, or vendor token in a `--author` or `--trailer` value blocks, because there is no subject-of-the-work reading of a byline field. One accepted cost falls out of this. A real person named Claude, or a collaborator whose address carries a token the matcher watches, is blocked from an author or trailer field, because a pre-commit string cannot tell the model "Claude" from a person named Claude. Blocking is the safe direction here: the primary author this hook guards is itself an assistant, so a field reading "Claude" is the intended catch far more often than a false one, and the fix is a one-word edit and a rerun.

## How to respond

When the hook stops the action, edit the message to remove the attribution, then run the command again:

1. **Delete the credit line or trailer.** No "generated with", no `Co-Authored-By` naming a model, no "AI-assisted" sign-off.
2. **Keep the message about the work.** A commit message explains why the change was made; a PR body explains what it does and how to verify it. Neither needs to say what wrote it.
3. **If a real person co-authored, name the person.** A `Co-Authored-By:` trailer for a human collaborator is correct and stays; only tool and model credits are removed.

The standard is zero AI attribution anywhere in the record: commits, PR titles and bodies, issue and review comments, docs, and code comments.

## Implementation

The executable is [`no-ai-attribution.py`](no-ai-attribution.py), a stdlib-only Python hook (no dependencies, one file for every OS, no separate Windows port). Wire it as `PreToolUse:Bash`, invoked as `python3 hooks/no-ai-attribution.py` (or `python hooks\no-ai-attribution.py` on Windows). It reads the Claude Code PreToolUse payload on stdin, and:

- exits `0` to let the command run, or exits `2` with a reason on stderr to deny it. The reason names what matched (message text, an author/trailer field, or a file) so the fix is obvious.
- reads the command from `tool_input.command`, splits it into logical lines on unquoted newlines and then into segments on shell operators, and only inspects segments that name one of the watched subcommands above. It tracks the effective directory across `cd`, `git -C`, and `env -C` so a relative file argument resolves where the command would read it. A named file is read only if it is a regular file, and only up to a byte cap, so a FIFO or a huge file cannot make the hook block or exhaust memory.
- uses two detectors for the two kinds of surface. Free prose (message, body, title, a named file's contents) goes through a nuanced check that fires on an attribution phrase, the emoji byline, or a `Co-Authored-By` line, but not a bare tool mention. Authorship fields (`--author`, `--trailer`, and a `Co-Authored-By` value) go through a strict check where any tool or bot token blocks.

It fails open: a payload it cannot read (malformed JSON, empty stdin, a non-Bash tool, a command with unbalanced quotes it cannot tokenize, or a named file it cannot open) allows the action rather than wedging the session. It never silently disables itself, though. An unexpected internal error is written to stderr before it allows. The contract is pinned by `hooks/tests/test_no_ai_attribution.py`: the commands that must block, the ones that must pass, and the fail-open cases.

## Blocking vs advisory

This ships as a blocking hook: it returns a `deny` decision so the commit or PR command does not run until the attribution is gone. Authorship in history is expensive to rewrite after the fact (a force-push to amend a pushed commit, an edit to a merged PR body), so this is one of the cases where stopping the action beats surfacing a warning that can be scrolled past.

If you would rather be reminded than gated, wire it as advisory the way `archive-reminder` and `verification-reminder` run in this collection: surface the matched line as context and let the command proceed. Advisory keeps the friction low; blocking guarantees nothing slips into the record. Pick by how reversible the surface is. For pushed commits and merged PRs, blocking is the safer default.
