# No AI attribution

When a `git commit`, a `gh pr create`, or a `gh pr comment` is about to run, check the message it carries for AI authorship credit and stop the action if it finds any. The published record of who wrote what should name people, not tools. A "generated with" line in a commit, a `Co-Authored-By` trailer naming a model, or a tool credit in a PR body all put a machine's name where a contributor's belongs, and once it is in git history or on a merged PR it is part of the project's provenance for good.

For a newsroom the stakes are higher than tidiness. Bylines and authorship are an editorial commitment: a reader, an editor, or a source who follows the trail should find the person accountable for the work, not a model version. This hook keeps that line clean at the moment the credit would otherwise enter the record.

## When it runs

On a `Bash` tool call whose command writes a message into the project record:

- `git commit`, checked against the commit message whether it is inline (`git commit -m`, `git commit -am`) or read from a file the command names (`git commit -F <file>`, `git commit --file <file>`, or a `git commit -t <file>`/`--template <file>` whose contents preload the message), and including a `git commit` chained after `&&`, `||`, `;`, or a pipe. Its author and trailer fields (`--author`, `--trailer`) are checked too, since those write authorship directly into the commit.
- `git merge`, checked against the merge commit message (`git merge -m <msg>`/`--message`, or `-F <file>`/`--file`), which git records for a non-fast-forward merge. It has no `--author`/`--trailer`, but its identity comes from the same environment and `git -c` config a commit uses, so those are read the same way.
- `gh pr create` and `gh issue create`, checked against the body (inline `--body`, a named `--body-file <file>`, or a `--template <file>`) and the title (`--title`). With `--body-file`/`--template` and no `--title`, `gh` prompts for the title interactively after the hook runs, so the title is not seen in that case.
- `gh pr edit` and `gh issue edit`, checked against the new title (`--title`) and body (`--body` or `--body-file <file>`), since editing after creation is another way a credit reaches the record.
- `gh pr merge`, checked against the merge or squash commit message it sets (`--subject`/`-t`, `--body`/`-b`, or a `--body-file`/`-F`) and against its author email (`--author-email`/`-A`), which sets the merge commit author and so is read strictly like a `git commit --author`. The merge-method flags `-m`/`--merge`, `-s`/`--squash`, and `-r`/`--rebase` carry no message and are left alone, so a clean `gh pr merge 123 -m` passes.
- `gh pr comment`, `gh issue comment`, and `gh pr review`, checked against the comment or review body, including a `--body-file <file>` body.
- `gh pr close`, `gh pr reopen`, `gh issue close`, and `gh issue reopen`, checked against the `--comment`/`-c` body they can post while changing state.
- `gh api`, checked against the record text it writes through a field or a request-body file: a `-f`/`--raw-field` or `-F`/`--field` value on a prose key (`body`, `title`, `message`, `note`, `description`), a `-F key=@<file>` that reads that value from a file, and a `--input <file>` JSON request body (parsed, its prose fields scanned). A nested/bracketed key naming a prose field (`input[body]`, as gh sends structured parameters and GraphQL variables) is read the same way, and a field value written with ANSI-C quoting (`-f body=$'...'`) is decoded before the check, like a commit message. A control field such as `state=closed`, and an explicit read-only method (`--method GET`/`-X GET`, which turns the fields into query parameters), are not flagged.

Anything else passes straight through. The check reads the message text the command submits, not the diff: inline, from a file the command names by path, or from an author/trailer field. A file argument of `-` (`git commit -F -`, `gh pr create --body-file -`) reads the message from stdin, which a pre-command hook cannot inspect, so those forms are not checked. The same holds for a message the shell computes at run time rather than one written literally: a command substitution or process substitution (`git commit -m "$(cat MSG)"`), or a message file created earlier in the same command line (`printf '...' > MSG && git commit -F MSG`), has no literal text for a pre-command check to read at hook time, so it passes. Catching the same-command file case would mean modeling the output of every writer (`printf`, `echo`, `tee`) and scanning every command's arguments, which would defeat the subject-of-the-work allowance. A commit that reuses an existing commit's message and authorship (`git commit -C <rev>`/`--reuse-message`, `-c <rev>`/`--reedit-message`) is the same case: the message lives in the referenced commit, not the command, so reading it would mean resolving an arbitrary revision and running git at hook time. The attribution, if any, entered history in that referenced commit, where it was the byline to catch; reusing it is not re-scanned here.

A commit's `--author` and `--trailer` fields, `gh pr create --template <file>`, and the whole `gh pr edit` subcommand were the flag-level bypasses of an earlier message-text-only guard; the executable closes them (#177). An author or trailer field is read as authorship: a tool or bot name there blocks even with a human-looking email, because an author field is a byline by definition. A template file is read like a message file: gh's `--template` like a `--body-file`, and git commit's `-t`/`--template` like a `--file`. Git's long options are matched the way git resolves them: an unambiguous prefix counts, so `git commit --au "Claude <c@example.com>"` sets the author and is read as one, while an ambiguous prefix that git itself rejects (`--a`) is left alone. gh does not prefix-match, so its flags are matched only in full. A bare `--` ends option parsing for git and gh alike: a byline-looking token after it is a pathspec (a filename), not message text, so `git commit -- --message "..."` is not scanned as a message.

The command word is found even when it is not the first token. Leading environment assignments and an `env` wrapper are stepped over (`GH_TOKEN=x gh pr create ...`, `env GIT_AUTHOR_NAME=Claude git commit ...`), with `env` matched by basename so a pathed `/usr/bin/env GIT_AUTHOR_NAME=Claude git commit ...` is peeled the same way. This includes the `env -S` split-string form in its spaced, attached, and `=` spellings (`env -S "..."`, `env -S'...'`, `env --split-string=...`), whose packed command is expanded and checked. An `env -C <dir>` run directory is honored in the same three spellings (`env -C dir`, `env -Cdir`, `env --chdir=dir`), and an `env --` that ends option parsing still has its following `NAME=value` operands read as assignments. Commands separated by shell operators or by a newline are each checked, whether or not the operator is spaced (`a&&git commit ...`, `(git commit ...)`, and a `git commit` on its own line after another command); a run of operator characters that the tokenizer glues into one token, such as a subshell close and separator (`(cd x); git commit ...`), still splits the commands. A command hidden behind a leading shell control keyword (`if ok; then git commit ...`, `while git commit ...`) is reached by peeling the keyword. A command-runner wrapper that executes the command word after it is peeled the same way, so the real command is still seen: `command git commit`, `exec git commit`, `nohup git commit`, and `setsid git commit` all run `git commit`, and the wrapper's own leading flags (`command -p`, `exec -a <name>`, `setsid -w`) are stepped over. A `command -v`/`-V <name>` is left alone, since that looks a command up rather than running it. Value-arg scheduling wrappers (`sudo`, `timeout`, `nice`, `ionice`, `stdbuf`) are not peeled: each would need its own option grammar, and prefixing an attributed commit with one is a contrived path the global commit guard and human review still cover. The command word is matched by its basename, so an interpreter invoked by an absolute or relative path (`/usr/bin/git commit ...`, `./gh pr create ...`) is still recognized, while a lookalike whose name only ends in the watched word (`mygit`) is not. A shell runner invoked with `-c` is followed into its script: `bash -c '...'`, `sh -c '...'`, and a pathed or clustered form (`/bin/bash -c '...'`, `bash -lc '...'`) have their script argument re-parsed as a command line and checked the same way, bounded by a recursion depth cap so a pathological nest cannot run away. A value-taking shell option before `-c` is stepped over so it does not hide the script (`bash -o pipefail -c '...'`, `bash --rcfile <file> -c '...'`), and an `env -C <dir>` in front of the runner moves where a relative file inside the script resolves. Shell redirections are stripped before the command word is read, so a redirect neither hides the command nor strands its message flag: `>/dev/null git commit -m "..."`, `git commit >/dev/null -m "..."`, and `git commit 2>/dev/null -m "..."` are each read as the git commit they are. A `gh` write command is recognized by its group and subcommand tokens regardless of any global flags before them (`gh -R owner/repo pr create ...`, `gh --hostname h pr create ...`). Commit identity set outside the message is read as authorship, the same as `--author`: the environment vars (`GIT_AUTHOR_NAME`, `GIT_COMMITTER_NAME`, and their email vars), whether set as an inline prefix or exported by an earlier `export` in the same command, and the inline config form `git -c user.name=... -c user.email=... commit`. The tracked identity follows the shell: a later `export`, a standalone reassignment of an already-exported var, or an `unset` updates it, an `env -u <NAME>` drops that one var for the command, and an `env -i` starts the command with an empty environment so an identity set earlier is not counted against it (an inline assignment after `env -i` is still passed and still read). A message written with ANSI-C quoting (`git commit -m $'subject\n\nGenerated with Claude'`), where the shell turns `\n` into a real newline before the command runs, has those escapes decoded so the byline lands on its own line the same way the shell will write it.

A named message file is read from the directory the command would run in, not blindly from the payload's `cwd`: a preceding `cd <dir>`, a `git -C <dir>`, or an `env -C <dir>` moves where a relative `-F`/`--body-file`/`--template` path resolves (`cd repo && git commit -F MSG` reads `repo/MSG`). Directory tracking is a best effort, because a pre-command hook cannot run the shell: a `cd` inside a subshell (`(cd repo); git commit ...`) does not actually persist, and a `cd` to a missing directory does not actually move. So a relative file is resolved against both the tracked directory and the payload's `cwd`, and a match in either blocks. Reading both makes a wrong guess about the directory a false positive at worst, never a missed byline. A `~`-prefixed file is read both as a literal `cwd`-relative path and as a home-expanded path, since the quoting that decides which the shell means is gone by tokenization; either interpretation blocks. Only a regular file is read, up to a size cap; a FIFO or device named as the file is treated as unreadable and passes, so the hook cannot block on a read.

One known false positive follows from splitting a command on its newlines: a watched command written inside a here-document body (`cat <<'EOF' > notes.txt` ... `git commit -m "..."` ... `EOF`) is checked as if that body line were a real command, so an attributed example inside documentation can trip the hook. The body is data, not a command the shell runs, so this over-blocks in the safe direction; the fix is to reword the example or split it across a run.

Because the hook binds to the `Bash` tool, it only sees these commands when they run as shell calls. A commit, PR, or comment made through a non-Bash path (an IDE's git integration, the GitHub web UI, or an MCP GitHub connector) does not pass through it, so it guards the command-line workflow rather than every write to the record. A message posted through a raw `gh api` call (for example a review-thread reply to `repos/{owner}/{repo}/pulls/{n}/comments/{id}/replies`) is inspected for the prose keys listed above (`body`, `title`, and the rest), but only where the value is a literal field or a readable `--input`/`@<file>` file: a body the shell computes at run time (`-f body="$(cat NOTE)"`) has no literal text at hook time and passes, the same limit as a computed commit message.

Two command forms carry no message text for a pre-command check to read, so they pass through: a bare `git commit` that opens an editor for the message (no `-m` or `-F`), and `gh pr create --fill`, `--fill-verbose`, or `--fill-first`, which assemble the title and body from the branch's commits. A filled body is only as clean as those commits. The hook screens the commit messages it can read, but a `--fill` body can also draw on commits it never screened: ones that predate its install, ones made through a path it does not watch (an IDE, the web UI, a connector), and even command-line commits whose message it could not read (a bare-editor commit, or `-F -` from stdin). So `--fill` is not a guarantee that the resulting body was screened.

## What it does not catch

The hook's job is to stop AI attribution from entering the record by accident — the credit an assistant appends to a commit or PR in the normal course of work. It is not an adversary barrier. A user set on writing a byline past it can, through forms no ordinary workflow produces, and those are left uncaught on purpose rather than chased into fragile parsing:

- **An append-assignment prefix.** `PATH+=:/usr/bin git commit -m "..."` uses the `NAME+=value` append form as a command prefix. Only the plain `NAME=value` assignment is recognized as an env prefix, so the append token reads as the command word and the commit is not seen.
- **An inline or ambient alias.** `git -c alias.ci=commit ci -m "..."` defines an alias inline and runs it; a `ci` alias in `~/.gitconfig`, or a shell `alias gc='git commit'`, does the same from outside the command. The hook matches the real `commit`/`merge` subcommand, not an alias that expands to it, which it cannot resolve without reading git's config or the shell's alias table.
- **Identity inherited into a subshell.** `export GIT_AUTHOR_NAME="AI ..."; bash -c 'git commit ...'` exports the identity in the parent shell; the recursion into the `-c` script starts a fresh identity context and does not carry the parent's exported vars in, so an env identity set outside the subshell is not applied to the inner commit.
- **Config reached indirectly.** `git -c user.name=$VAR commit` or `git --config-env=user.name=ENVVAR commit` names the identity through a variable the hook does not expand, so a tool name reached that way is not read.
- **A nest past the depth cap.** `bash -c` recursion stops after a fixed depth, so a byline buried under more shell-runner layers than the cap is not reached. The cap is the never-wedge guarantee: bounded work beats unbounded recursion on a hostile input.

These share a shape — each takes a deliberately unusual construction, not a form an assistant emits or a normal script writes. They are covered in depth by the layers around this hook: the fleet's global commit guard, the human reading every diff, and the PR review gate. This hook closes the accidental path; those close the deliberate one.

## What it flags

The message is refused when it carries author credit to an AI tool, model, or vendor. The patterns it looks for:

- An attribution verb (generated, created, written, authored, made, built, produced, assisted, co-authored, powered) joined by "with", "by", "using", or "via" to an assistant, model, or company name, when it leads a line: "Generated with Claude Code", "Written by ChatGPT", "Generated using Claude Code". The credited name covers the common assistants, models, and vendors (Claude, ChatGPT, GPT-*, Codex, Copilot, Gemini, Cursor, Anthropic, OpenAI, and the coding agents Aider and Windsurf), plus, inside a byline only, the agent names that are also common human names (Devin, Cline) — so "Generated by Devin" is a byline while a `Devin Smith` author is a person. The credited name can be a bare "AI" with no model ("Generated with AI", "Written by AI"), and the verb can carry an "AI-" prefix ("AI-assisted by Claude", "AI-generated with GPT-4"). The standalone-"AI" credit is distinguished from the adjective "AI-<noun>" of subject matter, so "Built with AI-powered search" describes the feature and passes. "Leads a line" allows a leading sign-off or list marker before the byline, so one dressed as a changelog entry (`- Generated with Claude`, `+ Generated with Claude`, `1. Generated with Claude`, `> Generated with Claude`) still blocks.
- A `Co-Authored-By:` trailer whose name or email points at a model or tool rather than a person.
- "AI-assisted" or "AI-generated" standing on its own as a sign-off line, or a robot-emoji byline (the emoji leading a line, or sharing a line with an attribution phrase). A robot emoji embedded in ordinary prose, such as "fix the robot-emoji glyph in Slack", is subject matter and passes.

Naming a tool as the *subject* of the work is fine: "switch the parser to the new tokenizer" or "document the Claude API client" describes the change and is not a byline. The hook targets credit lines, not every mention of a tool. A bare model name on its own is treated the same way: in free prose it is subject matter, so a model-comparison list ("- Claude", "- GPT-4") passes, and a credit needs one of the cues above to block (a verb-plus-tool byline, the "AI-assisted"/"AI-generated" or robot-emoji sign-off, or a `Co-Authored-By` value). A bare name blocks only in an author or trailer field, where it is authorship by definition (see below). Line position is the discriminator for the verb-plus-tool form: "Generated with Claude Code" leading a line is a byline and is refused, while the same words mid-sentence describe the subject and pass ("handle summaries generated by Claude", "flag posts written by GPT bots"). The same holds for "AI-assisted"/"AI-generated": "detect AI-generated images in uploads" and "add AI-assisted analysis" describe what the change is about, so they pass, while a bare "AI-assisted" line at the end of a message reads as a byline and is refused. The trade is deliberate: a credit that names a tool mid-sentence rather than at the start of a line can slip, but the emitted attribution forms lead their line, and the tool-name, emoji, and `Co-Authored-By` checks cover the ones that actually get written.

The exception is the author and trailer fields. Those are strict: any model, tool, or vendor token in a `--author` or `--trailer` value blocks, because there is no subject-of-the-work reading of a byline field. A generic-AI identity blocks there too — an author of "AI Assistant", "AI Bot", "AI Agent", "AI Model", or "artificial intelligence" — while a required noun after "AI" keeps it off a person whose given name is "Ai". The agent names that collide with human names (Devin, Cline) are deliberately not strict-field tokens, so a `Devin Smith` or `Cline` author still commits; they block only inside a byline. One accepted cost falls out of the strict rule. A real person named Claude, or a collaborator whose address carries a token the matcher watches, is blocked from an author or trailer field, because a pre-commit string cannot tell the model "Claude" from a person named Claude. Blocking is the safe direction here: the primary author this hook guards is itself an assistant, so a field reading "Claude" is the intended catch far more often than a false one, and the fix is a one-word edit and a rerun.

## How to respond

When the hook stops the action, edit the message to remove the attribution, then run the command again:

1. **Delete the credit line or trailer.** No "generated with", no `Co-Authored-By` naming a model, no "AI-assisted" sign-off.
2. **Keep the message about the work.** A commit message explains why the change was made; a PR body explains what it does and how to verify it. Neither needs to say what wrote it.
3. **If a real person co-authored, name the person.** A `Co-Authored-By:` trailer for a human collaborator is correct and stays; only tool and model credits are removed.

The standard is zero AI attribution anywhere in the record: commits, PR titles and bodies, issue and review comments, docs, and code comments.

## Implementation

The executable is [`no-ai-attribution.py`](no-ai-attribution.py), a stdlib-only Python hook (no dependencies, one file for every OS, no separate Windows port). Wire it as `PreToolUse:Bash`, invoked as `python3 hooks/no-ai-attribution.py` (or `python hooks\no-ai-attribution.py` on Windows). It reads the Claude Code PreToolUse payload on stdin, and:

- exits `0` to let the command run, or exits `2` with a reason on stderr to deny it. The reason names what matched (message text, an author/trailer field, or a file) so the fix is obvious.
- reads the command from `tool_input.command`, splits it into logical lines on unquoted newlines and then into segments on shell operators, and only inspects segments that name one of the watched subcommands above. It tracks the effective directory across `cd`, `git -C`, and `env -C` so a relative file argument resolves where the command would read it. A named file is read only if it is a regular file, and only up to a byte cap, so a FIFO or a huge file cannot make the hook block or exhaust memory.
- uses two detectors for the two kinds of surface. Free prose (message, body, title, a named file's contents) goes through a nuanced check that fires on an attribution phrase, the emoji byline, or a `Co-Authored-By` line, but not a bare tool mention. Authorship fields (`--author`, `--trailer`, and a `Co-Authored-By` value) go through a strict check where any tool or bot token blocks.

It fails open: a payload it cannot read (malformed JSON, empty stdin, a non-Bash tool, a command with unbalanced quotes it cannot tokenize, or a named file it cannot open) allows the action rather than wedging the session. It never silently disables itself, though. An unexpected internal error is written to stderr before it allows. The contract is pinned by `hooks/tests/test_no_ai_attribution.py`: the commands that must block, the ones that must pass, and the fail-open cases.

## Blocking vs advisory

This ships as a blocking hook: it returns a `deny` decision so the commit or PR command does not run until the attribution is gone. Authorship in history is expensive to rewrite after the fact (a force-push to amend a pushed commit, an edit to a merged PR body), so this is one of the cases where stopping the action beats surfacing a warning that can be scrolled past.

If you would rather be reminded than gated, wire it as advisory the way `archive-reminder` and `verification-reminder` run in this collection: surface the matched line as context and let the command proceed. Advisory keeps the friction low; blocking guarantees nothing slips into the record. Pick by how reversible the surface is. For pushed commits and merged PRs, blocking is the safer default.
