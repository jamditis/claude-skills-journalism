Development skill

Surface completeness

Updated Oct 23, 2026

Check that a shared interface change reaches every intended consumer, state, and guide.

Use this skill when

  • A cosmetic or shared component change affects more than one surface.
  • You must preserve an accepted design baseline while changing presentation.
  • Code, browser evidence, screenshots, and guidance must describe the same result.

Coverage workflow

Record the baseline

Keep the accepted result, intended change, affected surfaces, and recent work in your task list or plan tool.

Change the shared owner

Update the semantic token, component, or style rule once. Trace aliases, variants, generated output, and local overrides.

Keep one reviewer

Use one dedicated reviewer when supported. Check design rules, consumer coverage, relevant states, and documentation after each cosmetic change.

Reconcile evidence

Use static inspection for propagation and browser evidence for layout and interaction. Keep source, tests, deployment, persisted content, and public visibility separate.

Choose the relevant quality signals

Match the checks to the user task and the change. A copy edit does not need every audit. Record passed, not tested, and not applicable separately, with the build, browser, method, and evidence.

  • Accessibility: Combine automated scans with keyboard completion, focus and announcements, zoom, reflow, and relevant assistive-technology checks. A scan alone cannot establish conformance.
  • Browser support: Check the project's supported environments and feature-specific compatibility. Use a usable fallback for newer features. An emulated viewport is not a real-device test.
  • User preferences and lifecycle: Check affected reduced-motion, forced-colors, theme, long-content, loading, empty, error, retry, offline, and permission states.
  • Performance: Compare affected assets, fonts, layout shifts, and interaction work against the baseline. Keep field results separate from lab diagnostics.

Current performance indicators

Google's good Core Web Vitals targets use the 75th percentile of field measurements, segmented by mobile and desktop. They are experience guidance, separate from WCAG conformance.

Good Core Web Vitals field results
SignalGood resultWhat it measures
LCPAt most 2.5 secondsLoading
INPAt most 200 millisecondsInteraction responsiveness
CLSAt most 0.1Layout stability

A Lighthouse score does not prove field performance. If real-user data is unavailable, record that limit and use lab runs to diagnose the affected experience.

Standards and current resources

  • WCAG 2.2 defines the normative accessibility criteria. Use the project's required level and the criteria's scope and exceptions.
  • WAI evaluation guidance and APG keyboard guidance support manual checks and custom-widget behavior.
  • MDN Baseline describes browser support. It does not certify accessibility, usability, or performance.
  • Core Web Vitals and lab versus field data explain the performance measures and their limits.

The quality-signals reference maps changes to checks, source links, thresholds, and an evidence record. Sources checked October 28, 2026; recheck precise requirements before using them for a new decision.

Standards boundary

WCAG 2.2 success criteria are normative. Button hierarchy from USWDS, GOV.UK Design System, and Material Design 3 is design guidance. The standards reference keeps those roles separate.
